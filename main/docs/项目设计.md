# Educational Skill Builder：首版设计与实现说明

更新：2026-09-07。目标：一周内完成可演示、可接入真实模型的最小闭环。

## 1. 已确定的路径

教师可以先浏览社区助手并查看、试用；也可以进入创建流程：描述需求 → 教学功能解析 → 确认 Skill Card → 上传材料 → 生成 Agent → 检测 → 试用 → 报告 → 教师决定启用。

界面固定为六步：教学需求、功能解析、能力确认、教学材料、检测与试用、确认使用。第 4 步确认材料后生成 Agent；每次只进入相邻下一步。项目使用 `completedThrough` 保存进度，重新打开时进入最近未完成步骤；不另建知识库管理平台。

首个演示样例是七年级数学“一元一次方程作业讲评”。真实设计接口接受教师自由描述的学科和任务；无模型接口时使用明确标注的数学样例，不能声称已经实现通用自动生成。

## 2. 模块设计

### 2.1 教师账户与项目

- 设计逻辑：教师登录后可保存、重新打开自己的智能体；访客可先体验完整样例。
- 教育逻辑：教师保留方案确认权和是否使用的决定权。
- 技术逻辑：账户与项目按用户 ID 隔离；密码使用 scrypt 加盐哈希，随机会话使用 HttpOnly、SameSite Cookie。访客项目仅存在当前浏览器。
- 技术：Express、Node crypto、SQLite、localStorage（仅访客草稿）。本地 Demo 不含邮件验证、找回密码或学校单点登录。

### 2.1.1 教师助手社区

- 设计逻辑：商店首页负责发现，详情页解释教学对象、问题、方法和公开材料，试用页提供只读对话。
- 教育逻辑：先理解教学设计再试用，不用热度或评分代替教师判断。
- 技术逻辑：社区示例与教师私人项目分开；切换页面不清除创建草稿。首版使用前端静态数学示例，不提前建设发布、审核和推荐系统。
- 技术：Hash 路由、React 页面组件、shadcn 基础控件。

### 2.2 教学需求与功能解析

- 设计逻辑：一个自然语言输入框，提供可选数学示例。生成后用可编辑的教学对象、目标、任务、边界给教师确认。
- 教育逻辑：先说明要让谁学会什么、通过什么任务观察，再决定智能体的行为。这里采用目标与任务对齐的设计原则，不宣称自动识别了学生真实水平。
- 技术逻辑：通用设计模型输出结构化 JSON；后端校验必需字段、长度、Skill 数量。失败时显示错误并允许重试，不静默替换成示例。
- 技术：可配置 Chat Completions 兼容接口、结构化提示词、Zod 校验。

### 2.3 Skill Card

- 设计逻辑：每张卡片展示名称、用途；展开查看教育逻辑、技术逻辑和执行指令。教师可以启用/停用、调整指令。
- 教育逻辑：把“启发式”“形成性反馈”转化成可观察动作，例如先询问解题过程、根据具体错误给一步提示、再让学生尝试。是否直接给答案取决于教师需求；教师备课和学生辅导的规则不同。
- 技术逻辑：卡片是同一份 Skill 数据的可视化形式。`instruction` 会真实拼入教学模型的系统指令；卡片描述本身不能证明模型会执行。首版 Skill 属于指令型能力，不包含任意代码执行、外部工具或模型权重更新。
- 技术：TypeScript 类型、JSON、提示词组合。每张卡保留对应教师需求的 `reason`。

### 2.4 教学材料

- 设计逻辑：上传即可；展示文件名、读取状态和文字预览。不分类、不打标签。可使用自编数学示例材料。
- 教育逻辑：材料为知识解释、题目和参考答案提供依据。学生当次回答作为会话输入，不沉淀成公共资料。教材与答案存在冲突时说明冲突，交由教师确认，不按固定“教材总是优先”的规则覆盖评分依据。
- 技术逻辑：读取 PDF、DOCX、TXT、MD 文字，保留文件名；将少量完整文字附在模型上下文中。材料被明确界定为参考数据，其中的指令不能修改教师规则。上传不等于已成功读取。
- 技术：pdf-parse、mammoth、Multer 内存上传。每份最多 5MB、16,000 字符，合计最多 24,000 字符、最多五份；超限明确拒绝，不静默截断。首版不做 OCR、PPT、向量库、切片检索。扫描件或公式提取失败提示改用可复制文字材料。
- 使用：回答尽量注明真实文件名；不生成未经验证的页码。资料不足时说明不足，可以在明确区分的前提下提供一般解释，不伪装成材料内容。

### 2.5 Agent 生成与对话

- 设计逻辑：确认名称、已选 Skill 与材料后点击生成。无需教师理解模型设置。
- 教育逻辑：生成的是教师可检查的教学方案；运行表现仍需要后续验证。
- 技术逻辑：Agent = 微调模型接口 + 已确认教学目标 + Skill 执行指令 + 材料文字。保存配置版本，并在每次教学对话中携带。不是训练新模型。修改需求、Skill 或材料后清空旧检测、对话和启用状态，重新生成版本。
- 技术：独立设计模型与教学模型适配器、服务端环境变量、带超时的 fetch。密钥不进入前端。使用模型是否支持 system 指令、上下文容量及中文数学能力，需要拿到接口后实测。

### 2.6 Evaluation：技术与教育双维检查

- 设计逻辑：一键运行少量场景测试，逐条展示输入、真实回答、检查结果与理由。避免只有一个神秘总分。
- 教育逻辑：围绕已确认目标检验：回答是否切题、反馈是否针对学生证据、引导是否适合对象、是否遵守教师约定。诊断应表达可能原因，不能仅凭一道题断言学生能力。
- 技术逻辑：先检查配置完整性与材料可读性；真实模式由设计模型生成三个测试问题及预期行为，调用教学模型，再由设计模型依据规则给出辅助评价。记录实际回复、延迟、版本、模式。模型评价与程序确定性检查分开展示。
- 技术：固定 JSON 测试格式、程序断言、LLM 辅助评审。设计和评审可以复用一个通用接口以保持简单，但存在同源偏差；不能把自评当成教育有效性的独立证明。
- 演示模式：配置检查真实运行；模型执行与教育效果项目标为“待真实模型验证”，不给模拟通过率。

### 2.7 教师试用

- 设计逻辑：教师扮演实际使用者对话，提供一句反馈和“符合需求/需要调整”选择。
- 教育逻辑：教师对课程与学生的了解用于补充自动评价，重点判断是否有助于下一步教学，而不是只看回答是否流畅。
- 技术逻辑：保存当前版本的真实会话、模式和教师反馈。演示对话是明确标记的固定示例，只用于走流程。
- 技术：普通消息列表、后端模型调用，不为 Demo 引入流式输出或复杂对话编排。

### 2.8 报告与启用

- 设计逻辑：一页汇总需求、Skill、材料、测试证据、教师试用反馈和使用决定；可下载 Markdown 报告。教师可返回修改。
- 教育逻辑：报告区分功能适配、可观察教学行为与尚未验证的学习效果；一次试用不能证明提升学习成绩。
- 技术逻辑：报告来自当前配置和记录，不编造测试。启用要求完成检测、至少一轮试用和正向教师确认；真实模式存在未通过测试时阻止启用并提示调整。演示只能“保存为演示智能体”，不能当成正式通过。
- 技术：Markdown 导出、项目状态。启用范围仅当前平台，不自动发布公网、建立学生账户或接入学校系统。

## 3. 架构与数据

```text
React 教师工作台
       │ 同源 API
Express 服务
  ├─ 账户与项目 → SQLite
  ├─ 材料读取 → 文字 + 文件名
  ├─ 设计 / 辅助评审 → 通用模型接口
  └─ 教学 / 测试对话 → 已有微调模型接口
```

前端按工作流页面拆分；后端按账户、材料、模型、评测拆分。共享类型负责边界约定。项目配置保存为一个 JSON，避免过早拆成大量关系表。

| 数据 | 最少内容 |
| --- | --- |
| TeachingBrief | 教学对象、目标、任务、边界 |
| Skill | id、名称、用途、需求对应理由、教育逻辑、技术逻辑、执行指令、启用状态 |
| Material | id、文件名、提取文字 |
| AgentConfig | 名称、版本、Brief、已选 Skill、材料 |
| Evaluation | 版本、模式、时间、逐项输入/回复/结果/理由 |
| Project | id、名称、需求、配置、对话、检测、反馈、启用状态、已完成步骤 |

## 4. 模型配置与未完成依赖

设计器和评审器共用 `DESIGN_MODEL_*`；教学对话与测试执行使用 `TEACHING_MODEL_*`。配置全套后进入真实模式；缺少任一接口时使用显式演示模式，不将其中一个真实模型冒充另一个。

需用户提供两个接口的 Base URL、模型名称与密钥（若服务要求）。在服务端 `.env` 配置，不在聊天或浏览器中输入密钥。真实模型连接和效果验证要待这些信息具备后完成。

模型服务收到的内容包括需求、Skill、材料、对话；配置真实外部接口后这些数据将发送到对应服务。当前项目面向本机 Demo；公网运营需要另行配置 HTTPS、备份与生产部署。

## 5. 执行顺序与验收

1. 固化本设计，搭建六步工作台和数学样例。
2. 接上材料解析、配置组装、模式标识及错误处理。
3. 实现本地账户、项目保存、检测、试用与报告。
4. 接好两个真实模型的接口适配层，待凭据就绪后联调。
5. 检查桌面/手机布局，以及创建、修改失效、上传失败、注册登录隔离、报告导出全流程。

首轮验收：新用户能从描述需求走到保存演示智能体；上传文字确实进入配置；修改上游会使旧结果失效；无接口时始终提示演示；刷新后能恢复项目。真正的模型验收另用真实接口完成，不能由界面测试代替。

## 6. 当前教育依据与技术参考

本项目将目标对齐、逐步支架、形成性反馈作为设计原则；这些原则尚不等于本智能体的实证教学效果。EEF 的反馈指南强调反馈服务于推进学习、学生实际接收和利用反馈，因此首版保留“学生尝试—具体提示—再次尝试”和教师试用确认。

- [EEF：Teacher Feedback to Improve Pupil Learning](https://educationendowmentfoundation.org.uk/education-evidence/guidance-reports/feedback/)
- [阿里云 Model Studio：文本生成接口与 messages](https://docs.modelstudio.console.alibabacloud.com/en/model-studio/text-generation)
- [pdf-parse：PDF 文字提取](https://www.npmjs.com/package/pdf-parse)
- [Mammoth：DOCX raw text](https://github.com/mwilliamson/mammoth.js)

这些链接分别支持反馈原则与接口实现方式；不作为当前 Demo 已通过教育验证的证据。
